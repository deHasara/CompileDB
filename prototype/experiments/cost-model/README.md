# Cost-Model Validation

This directory contains the experiment used to evaluate whether CompileDB's
estimated workload cost predicts measured PostgreSQL execution time.

## Paper correspondence

This experiment corresponds to **Section 7.3, "Is the cost model
predictive?"**, and **Figure 11** of *From E/R Database Abstraction to
Workload-Aware Relational Realization*.

The experiment uses one fixed workload and 500 randomly sampled valid
relational schema configurations. For each configuration, it records:

1. the workload cost estimated by CompileDB's analytical cost model; and
2. the total execution time measured by PostgreSQL for the same workload.

The final figure plots estimated cost against measured execution time with
logarithmic x- and y-axes. This experiment validates the cost model; it does
not search for or report the best mapping.

## Dataset

The paper uses the same synthetic e-commerce schema as Experiments 1 and 2:

- 34 entity sets;
- one 21-entity inheritance hierarchy with maximum depth 5;
- one 5-entity inheritance hierarchy with maximum depth 3;
- 13 weak entity sets;
- 20 M:1 or M:N relationship sets; and
- approximately 11 GB of relational data.

## Relevant files

| File | Purpose |
|---|---|
| `generate_node_sizes_query_freq_skew.py` | Generates cardinalities, relationship statistics, and unit query frequencies and writes them into the schema JSON. |

| `example2_e_commerce.json` | Input E/R schema. Preserve an unchanged copy of this file. |

The commands below use the canonical repository filenames. Downloaded copies
may contain suffixes such as `(2)` or `(6)`; rename them before running the
experiment.

## Reference environment

The paper reports the following environment:

- PostgreSQL 16;
- 20 CPU cores; and
- 32 GB RAM.

The supplied driver connects to PostgreSQL using the user `postgres` and the
password `password`. Update the connection settings in `test_file-1.py` if the
local PostgreSQL installation uses different credentials.

The Python environment must provide CompileDB's project dependencies,
including NumPy and Psycopg2, and must be able to import:

- `helper_functions`;
- `helper_functions_extended`; and
- `dbshell`.

Run all commands from the directory containing these modules and the two
experiment scripts.

## 1. Prepare the schema input

The generator modifies its input JSON **in place**. Create a dedicated copy so
that the original schema remains unchanged:

```bash
cp example2_e_commerce.json example2_e_commerce_cost_model.json
```

At the bottom of `generate_node_sizes_query_freq_skew.py`, set:

```python
load_file = "example2_e_commerce_cost_model.json"
init_node_sizes_and_query_frequencies(load_file)
```

The supplied script currently names `example2_e_com_small.json`; it must be
changed before generating the e-commerce experiment input.

## 2. Generate cardinalities and workload frequencies

The generator fixes both random-number generators to seed `1`:

```python
random.seed(1)
np.random.seed(1)
```

Run:

```bash
python3 generate_node_sizes_query_freq_skew.py
```

The script adds or replaces the following top-level fields in
`example2_e_commerce_cost_model.json`:

- `node_data`;
- `select_all_frequencies`; and
- `insert_frequencies`.

Validate that the resulting file is valid JSON:

```bash
python3 -m json.tool example2_e_commerce_cost_model.json > /dev/null
```

### Statistics generated by the supplied code

| Statistic | Generated value |
|---|---|
| Hierarchy leaf counts | Zipf distribution with `alpha = 2`; the least probable leaf has 100,000 tuples. |
| Non-leaf hierarchy counts | Sum of descendant counts multiplied by a Beta(1,10) sample scaled to `[0.005, 2.0]`. |
| Non-hierarchical strong-entity counts | Uniform integer from 100,000 through 250,000. |
| Weak-entity counts | Uniform integer from 100,000 through 150,000. |
| M:1 participation factor | Uniform value from 0.01 through 1.00. |
| M:N participation factor | Uniform value from 0.01 through 1.00 for `entity1`. |
| M:N `entity1`-to-`entity2` fanout | Uniform integer from 1 through 10. |
| Average multi-valued-attribute count | Uniform integer from 1 through 3. |
| Select frequency | `1` for every entity and relationship. |
| Insert frequency | `1` for every entity and relationship. |

Because `fraction = 1 / 1` in both frequency-generation functions, the current
code constructs the uniform all-components workload used by the cost-model
validation.

> **Implementation note:** the supplied generator uses 100,000--250,000 tuples
> for non-hierarchical strong entities, whereas Section 7.1 of the paper states
> a range of 10,000--150,000 for non-hierarchical entity sets. Align the code
> and paper before publishing a final artifact. The table above documents the
> behavior of the supplied code.

## 3. Configure random mapping sampling

`test_file-1.py` delegates configuration generation and measurement to
`run_different_configurations`, imported from the helper modules. The number of
sampled configurations is not set in either script included in this directory.

Before running the paper experiment, inspect the helper implementation and
confirm that it:

- samples exactly 500 configurations;
- samples only valid conceptual-to-relational mappings;
- uses a fixed and recorded random seed;
- evaluates every configuration using the same generated workload;
- records both estimated total cost and measured total execution time; and
- writes one result record per configuration to `output_cost_model.csv`.

The following command helps locate the relevant implementation:

```bash
rg -n "def run_different_configurations|output_cost_model" \
    helper_functions.py helper_functions_extended.py
```

## 4. Run the validation experiment

Use a fresh database name. The driver creates `erdb_objects` without
`IF NOT EXISTS`, so reusing an initialized database may fail or mix metadata
from an earlier run.

The command-line interface is:

```text
python3 test_file-1.py COMMAND DATABASE LOAD_FILE
```

Run the cost-model validation as follows:

```bash
python3 test_file-1.py \
    run_different_configs \
    cost_model_db \
    example2_e_commerce_cost_model.json
```

The argument order is important. `run_different_configs` is the command,
`cost_model_db` is the PostgreSQL database, and the final argument is the
generated schema JSON.

Internally, the driver performs the following steps:

1. creates the database if it does not exist;
2. constructs the E/R graph from the schema JSON;
3. generates one workload using `initialize_workload_generation`;
4. retains that workload and its relation-size metadata; and
5. calls `run_different_configurations` to estimate and measure the sampled
   mappings.

Do not regenerate the workload between configurations.

## 5. Collect and validate the results

The experiment writes its raw results to:

```text
output_cost_model.csv
```

Move any earlier output out of the way before starting a new experiment so
that records from different runs are not combined. Preserve the completed raw
CSV before post-processing.

The CSV must contain, directly or through equivalent columns, at least:

```text
configuration_id,estimated_cost,execution_time_ms
```

Before plotting, verify that:

- exactly 500 distinct configurations were evaluated;
- all configurations used the same workload;
- every estimated cost and execution time is finite and positive;
- failed or timed-out executions are reported explicitly rather than silently
  omitted;
- measured time is the total PostgreSQL workload time in milliseconds; and
- select-query timing follows the paper's protocol of five executions with the
  median retained for each query.

## 6. Reproduce Figure 11

Create a scatter plot using:

- x-axis: estimated workload cost;
- y-axis: measured total PostgreSQL execution time in milliseconds;
- logarithmic scale on both axes; and
- one point for each of the 500 sampled mappings.

Fit the trend line in log space:

```text
log10(execution_time_ms) = intercept + slope * log10(estimated_cost)
```

The figure should be labeled:

```text
Estimated Cost vs. PostgreSQL Execution Time
```

Keep the raw CSV, processed plotting input, fitted parameters, and final figure
as separate artifacts. If correlation statistics are reported, compute them
over the same 500 points shown in the figure.
